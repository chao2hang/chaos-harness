# Agent Note: 从设置中重启 Web 服务

Status: implemented

[English](2026-08-19-web-server-self-restart.md) | 中文

## Problem

有几类改动是在 Web GUI 里做出的，却无法在运行中的进程里生效。设置 seam 已按 namespace 声明 `applies: 'restart'`，插件的增删只有在全新的 Loader 树中才成立，而重新构建的模块代码对一个已经 import 过它的进程不可见。在此之前，要让其中任何一类生效，唯一的办法是找到启动 `dsh --profile web` 的那个终端手动重启——而从另一台机器访问的全网卡部署根本做不到这一点。

## Decision

重启是一次经启动器请求的进程替换，对外表现为一个 Host RPC 与一个设置分区。

`@deepseek-ai/dsh-cmdline` 在既有的 `ctx.appExit` 旁增加 `ctx.appRestart`。两者都是启动器事实，由 `provideCmdline` 在任何配置树条目挂载之前提供。`restart` 是 `CmdlineHost` 中唯一可选的成员：无法启动后继进程的启动器——嵌入宿主，或生命周期由监管进程持有的界面——会省略它，`ctx.appRestart` 保持缺失，消费方据此报告该能力不可用。在那里改用普通退出，只会让服务停下而没有任何东西接手，这严格劣于直接拒绝。

`apps/cli` 实现该请求。`createProcessShutdown` 增加了一个 `restart()`：它武装一次后继启动，而不是另辟一条路径——启动发生在既有控制器到达的任一终结点上：自然完成、拆卸被拒，或五秒强制退出。选择"武装"而非"拆卸完成后再启动"，正是为了让缓慢的拆卸仍然是一次重启，而不是悄悄退化为一次没有任何东西接手的关停。信号会解除武装：操作者要求该进程停止的意图高于排队中的重启，且不应交给它一个逃逸出杀死前驱进程的那套监管之外的后继进程。后继进程是 `spawn(process.execPath, [...process.execArgv, ...process.argv.slice(1)])`，detached 且继承 stdio：源码启动时 `execArgv` 携带 `--import tsx/esm`，而 `argv` 携带 profile、绑定主机、端口与 TLS 路径，因此后继进程服务于浏览器已经指向的那个 URL。

`host.restart` 是网关这一半。它先应答，`restartGraceMs`（默认 250 毫秒，`ApiProxyService` 的一个经校验配置项）之后才请求启动器，因为在调用内部拆掉自己的服务器根本无法作答。这段宽限为应答争取到一次 flush；它并不承重，因为无论如何调用方都会把这次交接观察为一次普通断连。`host.describe.canRestart` 报告该能力是否存在，使客户端可以直接不提供该控件，而不是提供一个注定失败的控件；缺失时请求回答 `restart-unavailable`。配置树拆卸会取消待执行的交接，因此因任何其他原因发生的拆卸都不会留下无人请求的后继进程。

`@deepseek-ai/dsh-client-ui-settings-maintenance` 是界面：一个 id 为 `maintenance`、order 为 30 的 `settings.section`。它自身不发起任何读取——状态与重启可用性都来自连接持有的、以连接代际为界的 Host 描述——并把请求挡在一个写明挂载会话数的风险确认框之后。

## Why the browser waits for a round trip

应答并不能证明后继进程的任何状态，因此分区把重启视为只能被观察为"先断连、后返回"：它等待 Host 描述先消失、再回来，只有两半都发生后才报告成功。前驱进程仍在应答期间重新发布的描述不会结束等待；被拒绝的请求也不会因为随后一次无关的重连而变成成功。这样做复用了连接既有的重连机制，而不必给传输层增加一个启动标识：浏览器本就会执行的那次重连，就是证据。

## Authorization

`host.restart` 在 `dsh-client-connection` 中受认证约束，而不像原生桌面方法那样固定在环回地址。重启会结束该宿主上的所有会话，因此它不应只由普通的浏览器信任栅栏把守；但全网卡部署恰恰是没人能够触及终端把服务重新拉起来的场景，而已认证的调用方本就能通过任意会话的工具以该进程的身份执行命令。把它钉死在环回地址，会是一道立在敞开大门旁边的栅栏，并且恰恰在它最要紧的地方移除了这项能力。

## Verification

关停控制器测试钉住了自然完成、拆卸被拒与宽限超时三条路径上的后继启动、信号对它的压制，以及重复请求只启动一次；另一个 spec 钉住源码启动与构建产物启动两种调用下的后继命令行。网关测试在 fake timer 下钉住"先应答后请求"的次序、同一段宽限内的合并、拆卸时的取消，以及 `restart-unavailable` 拒绝；schema 测试把两个能力标志钉为必需的传输字段。分区的组件 spec 覆盖确认门、完整往返，以及等待不得误判为成功的两种情形。已组装的浏览器场景覆盖诚实的不可用状态，因为 e2e 脚手架直接引导配置树而非经由启动器，因此不提供 `appRestart`。

单元测试触及不到的进程行为——启动器能否复现自身调用、后继进程能否在前驱之后存活、以及它是否绑定了前驱释放的端口——由 `apps/cli/tests/web-restart.e2e.ts` 针对一个真实由启动器引导的 `dsh web` 钉住。它证明后继进程存在的方式是：在被启动的那个进程自身以状态 0 退出之后，端口依然在提供服务。

## Alternatives considered

**就地重载 Cordis 配置树。** 这保持连接存活且快得多，但无法重新加载已经 import 的模块代码，而那正是开发者重启服务时最想要的部分。启动器本就为 `cordis.patch.yml` 编辑实时重组 patch 层，因此就地路径对它能服务的场景已经存在。

**让网关自己 spawn 后继进程。** 网关将不得不知道进程自身的命令行、它的运行时 flag，以及配置树何时拆卸完毕——这些全是启动器事实。经由 `ctx.appRestart` 转发，让进程生命周期留在本就持有它的那个组件里。

**给 `host.describe` 增加一个启动标识，让浏览器识别后继进程。** 这为了做出重连已经做出的观察而增加一个传输字段：新代际的描述之所以存在，正是因为旧连接死亡且新握手成功。

**约定一个退出码交给监管进程解释来完成重启。** 随发行版交付的 `dsh --profile web` 部署里并没有监管进程，而要求存在一个监管进程，会让这项能力恰恰在它被提出的场景中不可用。

## Consequences

用户可以从 GUI 应用只有重启才生效的设置、插件改动与重新构建的代码，远程部署同样适用。代价是前驱进程的会话、下行连接与进行中的轮次随它一同结束——确认框会说明这一点并写明数量。始终无法绑定端口的后继进程会让分区一直报告仍在等待；要区分启动缓慢与启动失败，需要 Host 消失之后浏览器无法获取的 Host 侧证据。

继承 stdio 会把一条约束带给 `dsh` 的启动方。终端、文件与 shell 重定向都能跨越这次交接存活，但读端就是那个正在退出的父进程的管道不能，后继进程会在第一次写入时死掉。捕获该进程输出的监管方必须交给它一个在重启期间保持打开的描述符——重启 e2e 正是这样做的，而改用管道正是它第一次运行失败的原因。
